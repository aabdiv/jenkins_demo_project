# demo-agent: учебный CI для FastAPI-сервиса в Jenkins

Маленький сервис с двумя эндпоинтами и пайплайн **Checkout → Setup → Lint → Test**.
Это дни 2–3 спринта по Jenkins. Сборка образа и деплой появятся на днях 4–8.

## Что внутри

| Файл | Зачем |
| --- | --- |
| `app/main.py` | Сервис: `GET /health` (проверка живости) и `POST /ask` (эхо-заглушка агента) |
| `tests/test_main.py` | Три теста на pytest через `TestClient` |
| `requirements.txt` | Зависимости самого сервиса |
| `requirements-dev.txt` | Плюс то, что нужно только в CI: pytest, httpx, ruff |
| `Jenkinsfile` | Пайплайн; комментарии внутри объясняют каждое решение |

## Запуск в Jenkins

1. Положите эти файлы в свой репозиторий на GitHub (можно в новый) и запушьте.
2. В Jenkins создайте **Multibranch Pipeline**, источник — **Git** (не GitHub: так Jenkins не тратит лимит GitHub API).
3. Нажмите **Scan Multibranch Pipeline Now**. Должна пройти зелёная сборка ветки `main`.

Локально, без Jenkins, то же самое проверяется так:

```
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/ruff check .
.venv/bin/python -m pytest -v
uvicorn app.main:app --reload   # затем http://localhost:8000/docs
```

## Задания на дни 2–3

1. **Зелёная сборка.** Найдите в логе: где создаётся venv, где ставятся пакеты, где запускается pytest. Откройте на странице сборки раздел **Test Result**: это отчёт из `reports/junit.xml`.
2. **Красная сборка.** Сломайте тест, например поменяйте ожидаемый статус на `201`. Запушьте и посмотрите, на какой стадии упало, что показывает Test Result и пришло ли письмо в Mailpit (`localhost:8025`). Почините — должно прийти письмо «снова зелёная» (блок `fixed`).
3. **Сломанный линтер.** Добавьте в `app/main.py` неиспользуемый импорт (`import os`). Стадия Lint должна упасть, а Test — даже не запуститься. Почему?
4. **Параметр.** После первой сборки на странице ветки появится **Build with Parameters**. Запустите с выключенным `RUN_LINT`: стадия Lint будет помечена как пропущенная.
5. **Где всё это лежит.** Найдите в контейнере Jenkins workspace этой сборки и в нём `.venv`, `.pip-cache` и `reports/`:
   `docker exec jenkins ls -la /var/jenkins_home/workspace/`
   Подумайте: зачем кэш pip в workspace и что будет со скоростью второй сборки?
6. **Параллельность.** Перепишите Lint и Test так, чтобы они шли одновременно (`parallel { stage(...) stage(...) }` внутри одной стадии). Что видно в логе и в графе пайплайна?
7. **Воспроизводимость.** Сейчас версии пакетов не зафиксированы: сегодняшняя и завтрашняя сборка могут получить разный FastAPI. Зафиксируйте их (`pip freeze > requirements.lock` или `pip-tools` / `uv`) и ставьте в CI из lock-файла.

## Что уже учтено в Jenkinsfile

- **Образ `python:3.12-slim`, а не alpine.** Для Debian есть готовые сборки (wheels) библиотек вроде pydantic-core. На alpine их может не оказаться, особенно для самой свежей версии Python, и pip начнёт компилировать их из исходников.
- **venv в workspace и вызов по полному пути `.venv/bin/...`.** Контейнер работает от uid 1000: ставить пакеты в системный Python ему нельзя. А каждый шаг `sh` — отдельная оболочка, поэтому `source .venv/bin/activate` из одного шага не действует в следующем.
- **`timeout`, `buildDiscarder`, `timestamps`** — базовая гигиена любого пайплайна.
- **Письма через Mailpit** — только при падении и при починке, чтобы не спамить на каждую зелёную сборку.

Предупреждение `StarletteDeprecationWarning` о httpx в выводе pytest на результат не влияет: это сообщение новой версии Starlette о смене клиента для `TestClient`.
